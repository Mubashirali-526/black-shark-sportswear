# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install        # install dependencies
npm run dev         # start dev server (http://localhost:3000)
npm run build       # production build
npm run start        # run production build
npm run lint          # eslint .
npm run typecheck    # tsc --noEmit
npm run db:seed      # tsx src/db/seed.ts — seeds categories/products/admin user into Supabase (idempotent)
```

There is no test script/framework configured in this repo. There is no `db:push`/`db:generate` script either — Drizzle migrations must be run manually via `npx drizzle-kit push` (see Database section below). `drizzle.config.ts` loads `DATABASE_URL` from `.env.local` via `dotenv` — it used to be a static `drizzle.config.json` pointing at a hardcoded local placeholder URL that didn't match the app's real DB; if you ever see a `.json` config again instead of `.ts`, that mismatch bug has regressed. This came up for real: a task once asked for `dbCredentials.url` to be the literal string `"${process.env.DATABASE_URL}"` inside a `drizzle.config.json` — that syntax only interpolates inside actual JS/TS, so in JSON it would've connected to that literal text. Declined and kept the working `.ts` config.

## Architecture

Next.js 16 App Router site (React 19, TypeScript, Tailwind CSS v4) for a sportswear brand ("Black Shark Sportswear"), now with a real Admin Dashboard (see that section below) on top of a Supabase Postgres database. **No longer frontend-only for everything** — `/products`, `/products/[slug]`, `/categories`, and `/categories/[slug]` read live from Supabase via `src/lib/site-data.ts` (falling back to the static arrays in `src/lib/data.ts` only if the DB is unreachable), and products added/edited/deleted through the Admin Dashboard show up on those pages immediately (all four routes are `force-dynamic`, no caching to invalidate). Most *other* pages (home, about, manufacturing, portfolio, gallery, etc.) are still fully static from `data.ts` — don't assume DB-backing spreads further than those four routes without checking `site-data.ts` first. There is no cart anymore (removed entirely, see Commerce flows). There is no blog (removed — see Data layer below).

### Data layer — `data.ts` is now the seed source + fallback, not the live source, for products/categories

`src/lib/data.ts` is still the origin of all site *content* and the thing you hand-edit for copy changes, but for the four DB-wired routes above it's no longer what actually renders — see "Public site ↔ Supabase" below for the live path, and the Database section for the schema. Everything below this line describes the static data as it still exists and still drives every other page + the DB seed.

- `src/lib/data.ts` is still the single source of truth for all *content authoring* — `products`, `categories`, `sports`, `galleryImages`, `testimonials`, `faqs`, `heroSlides`, `BRAND`, etc., plus their TypeScript types (`Product`, `Category`, `Faq`, `Testimonial`) — but for `products`/`categories` specifically, editing this file only changes the seed/fallback data, not what's live on `/products` or `/categories` (see Public site ↔ Supabase below). There's a real Admin Dashboard now (see that section) for changing live product/category data day-to-day; hand-editing `data.ts`'s `products` array (incl. its optional `sku` "Article No", format `BS-<CategoryLetter><NN>`, e.g. `BS-J01` for jerseys) is still how you change the seed/fallback content itself.
- **`products` (the `/products` listing's array, not `categoryProducts`) is now machine-generated from `categoryProducts`**, one entry per category item (~96 total), not hand-written demo data anymore. The mapping: `sport` defaults per category (`gym-wear`/`activewear` → "Running", `boxing-gloves` → "Boxing", everything else → "Soccer") except `team-uniforms`, which reads the item's own `tags` and maps "Basketball"/"Rugby" tags to that sport instead of the category default; `slug` is generated from the name (lowercase, hyphenated, deduped against collisions); the first two items in each category get `badge: "Best Seller"` / `"New"` respectively (everything else undefined); the first 8 products across the whole generated array (in `categoryProducts` object-key order) get `featured: true`; `colors`/`sizes`/`specs` reuse the existing `commonColors`/`commonSizes`/`baseSpecs` constants; `rating` (4.5–4.9) and `reviews` (50–300) are seeded-random. **`price` is `0` for every product and is never rendered anywhere** (see Products page section below) — don't reintroduce price display without being asked, and don't be surprised the field is `0` instead of missing; the type still requires it. If `categoryProducts` changes, this array needs regenerating to stay in sync — it does not derive live at build time, it was a one-time generation written directly into `data.ts`.
- **There is no blog anymore.** `blogs`/`Blog` (type and content) were removed entirely from `data.ts`, `src/app/blog/` and `blog-featured-carousel.tsx` were deleted, and nav/footer "Blog" links were replaced with "Portfolio" → `/portfolio` (see Portfolio page below). Don't reintroduce a blog data shape or route without being asked.
- `galleryImages` is hardcoded (not generated via the `l()`/`p()` Pexels helpers used elsewhere in this file) — 50 entries of `{ id, src, alt, tag }`, `id` is a stable identity used for error-hiding (see `gallery-grid.tsx` below), `src` points at Cloudinary (`res.cloudinary.com/b1wzngum/image/upload/f_auto,q_auto,w_800/bs-<n>.png|jpg`, mixed extensions per-file), entries are grouped consecutively by `tag` (5 per tag) rather than interleaved.
- `categories` (12 entries — Team Uniforms / Gym Wear / Outerwear Collection / Activewear / Custom Printing / Sublimation Wear / Hoodies & Jackets / Youth Sportswear / Boxing Gloves / Bags / Caps / Socks) is used by the `/categories` grid, with local `/categories/*.png|jpg` images — **but the homepage's "Featured Categories" section does NOT read from it.** `src/app/(site)/page.tsx` has its own separate page-local `featuredCategories` array (different images, plus a per-card `objectPosition` inline-style override used to fine-tune crops, e.g. Team Uniforms is `"center top"` to hide shorts and show only the shirt). Edit whichever one is actually asked for — a lot of back-and-forth in this repo's history has been re-editing the wrong one of these two. Four slugs were renamed partway through this repo's history and the rename was propagated everywhere: `training-wear`→`gym-wear`, `jackets-outerwear`→`outerwear-collection`, `accessories`→`custom-printing`, `fan-merch`→`sublimation-wear` — this touched `categories`, the matching `products[].categorySlug` values, `featuredCategories` in `page.tsx`, and the (otherwise-unused-in-render) `heroSlides[].target` fields; if a slug lookup ever seems to silently miss, check for old-slug leftovers in one of those four places. The `Category` type has an optional `placeholder?: boolean` — when true, `categories/page.tsx` skips rendering an `<Image>` entirely and shows a plain `bg-[#0a0a0a]` tile instead (no broken-image icon while real photos are pending); currently no category has it set since all 12 now have real photography, but the mechanism is still there for future categories. Also note: two `products` entries still carry the stale display string `category: "Training Wear"` (pre-rename label text, cosmetic only, filtering uses `categorySlug`) — left as-is.
- `/categories/[slug]/page.tsx` is a dynamic route (`generateStaticParams` over all `categories` slugs, `notFound()` for an unmatched slug) showing a dark product grid per category, sourced from a separate `categoryProducts: Record<string, CategoryProduct[]>` map in `data.ts`. **Two data shapes coexist** in `CategoryProduct` (`id`/`fabric` are optional, as is `tags?: string[]` and a per-product `position?: string`): 11 of the 12 categories have been fully migrated to local `/categories/<slug>/*.png` photos with a `tags` chip row instead of `id`/`fabric` — **only `socks` still has the original Cloudinary `bs-<n>.png` placeholder data** (`id` like `BS-SO-003` + a `fabric` spec line); the card template renders whichever fields are present, so don't assume every category has an `id`/`fabric`, and don't assume every category has real photos — check before editing. Categories with no `categoryProducts` entry fall back to an empty-state "Products coming soon" card. On `/categories` itself, a card only links to its `/categories/<slug>` detail page if `categoryProducts[slug]` has entries — otherwise it still falls back to `/products`.
- Image cropping on `/categories/[slug]/page.tsx` is controlled by **three independent per-category lookup maps** plus one per-product override, all in that file — real product photos vary wildly in orientation/margin, and each map exists to fix a different symptom, so check all of them (and the actual source image) before guessing at a fix: `categoryImagePosition` (`object-top` etc. — for portrait photos cropped by a too-short box; currently `gym-wear`, `outerwear-collection`), `categoryAspect` (overrides the default `aspect-[4/5]` box shape — currently `boxing-gloves` → `aspect-square`, since those photos are near-square and fill the frame edge-to-edge with no margin), `categoryFit` (overrides `object-cover` → `object-contain` — currently `bags` and `caps`, both of which mix landscape and portrait shots *within the same category*, so no single crop position or aspect ratio works for every product), and `CategoryProduct.position` (a per-*product*, not per-category, override — currently only set on one Outerwear Collection product, `"object-[center_30%]"`, that needed to differ from its category's own default). The separate `/categories` grid (not `[slug]`) has its own unrelated `cardImagePosition` map for the same class of problem on its own hero-tile images — the two files' maps don't share values or affect each other.
- Route handlers under `src/app/**/[slug]/` must treat `params` as a `Promise` and `await` it (Next.js 16 breaking change from earlier versions) — both `generateMetadata` and the page component. Using it as a plain sync object compiles fine but silently 404s every request at runtime; `products/[slug]/page.tsx` and `categories/[slug]/page.tsx` are the two current reference implementations of the correct pattern.
- `stats` (used only by the About page's stats bar) and `processSteps` (used by *both* the homepage's own Process section and, indirectly, `/manufacturing` — see below) are the other two `data.ts` arrays that got a content pass in this same period: `stats` is now `500+ Orders Delivered / 40+ Countries Served / 13+ Years Manufacturing / 100% On-Time Delivery`; `processSteps`' `image` fields now point at local `/manufacturing/*.png` files instead of the old root-level `manufacturing-consultation.jpg` etc. Changing `processSteps.image` here is safe for `/manufacturing` specifically because that page no longer reads it directly (see below) — but the **homepage's** Process section does still read `step.image` straight from this array, so an edit here still shows up there.
- API routes: `src/app/api/health/route.ts` (`503` if `db` is null, else `SELECT 1` → `200`/`500`) and `src/app/api/newsletter/route.ts` (`POST { email }`, validates, inserts into `newsletterSubscribers` with `onConflictDoNothing()` so re-subscribing an existing email is a no-op success, not an error).

### Public site ↔ Supabase (`src/lib/site-data.ts`)

The DB-first-with-fallback adapter layer for the four wired routes. Every exported function tries `db` first and only falls back to `data.ts` if `db` is `null` (unconfigured) or the query throws — **not** merely because a query legitimately returned zero rows (an empty, newly-created category is real data, not a failure, and should render its real empty state, not silently swap in static demo content).
- `getSiteCategories()` / `getCategoryProductCounts()` power `/categories`; `getSiteCategoryProducts(slug)` powers `/categories/[slug]` (maps a DB `products` row into the `CategoryProduct` shape — `image` is `images[0]`); `getSiteProducts()` / `getSiteProductBySlug(slug)` power `/products` and `/products/[slug]` (maps into the full `Product` shape). All four page routes set `export const dynamic = "force-dynamic"` so every request re-queries — this is *why* an Admin Dashboard change shows up immediately, there's no cache to invalidate.
- `/categories/page.tsx` and `/products/page.tsx` had to be restructured to fetch server-side and hand the data down: `products-explorer.tsx` now takes `products`/`categories` as props instead of importing the static arrays directly, and the old `categories/page.tsx` (client component, motion-animated) was split into a thin async server `page.tsx` that fetches, plus `src/components/site/categories-content.tsx` (client) that renders — same pattern to follow if another static-import page needs DB-wiring later.
- `mapDbProduct()` prefers real DB columns (`sport`, `badge`, `featured`, `price`, `oldPrice`, `colors`, `sizes` all exist as real columns now — see Database section) and only synthesizes a value when one is genuinely missing: `rating` falls back to a deterministic hash-seeded value (stable per product id, not random-per-request) if null; `sport` falls back to the old category-default mapping if null; `colors`/`sizes` fall back to the shared `commonColors`/`commonSizes` if the DB array is empty. There's **no more "auto-New-if-recently-created" badge fallback** — an earlier version of this file had one (for when `badge` didn't exist as a column yet), and once real badge data landed via the seed it started mislabeling most of the catalog as "New" because the whole DB was seeded within the same compressed session timeline; removed rather than special-cased.
- **Deliberately NOT wired**: the homepage's "Featured Categories" section (`src/app/(site)/page.tsx`) — see the comment directly above that array in the file. It's a hand-curated 6-of-12 subset with its own images/crops, distinct from the `/categories` grid on purpose; swapping it for a live DB query would silently replace the curated art direction with generic category photos. Flagged, not guessed, when this was requested. There's also no "featured products" section on the homepage to wire — "Our Expertise" and "Featured Build" are curated editorial content, unrelated to the `products` table.
- Also NOT wired (out of scope, never asked): `wishlist/page.tsx` (`products.slice(0,4)` demo seed), `checkout/page.tsx` (hardcoded demo line items), `order-form-modal.tsx` (uses static `categories` for a dropdown).

### Database (Supabase Postgres) — schema/seed exist; products/categories are now the live source for 4 public routes + all Admin Dashboard CRUD

`.env.local`'s `DATABASE_URL` points at a live **Supabase** Postgres instance (via its pooler, port 6543) — not Neon. `src/db/schema.ts` defines six tables: `newsletterSubscribers` (still used by `/api/newsletter`), `adminUsers`, `categories`, `products`, `quoteRequests`, `galleryImages` — all pushed live via `npx drizzle-kit push` and seeded via `npm run db:seed`. `products.categorySlug` has a real FK to `categories.slug`. The `products` table started as a mirror of `categoryProducts`' shape (`slug`, `name`, `categorySlug`, `description`, `fabric`, `tags[]`, `images[]`, `position`) but has since grown 9 more columns to match the richer static `Product` type: `sport` (text), `badge` (text — `'New' | 'Best Seller' | 'Sale' | null`), `featured` (boolean, not-null default `false`), `rating` (real, nullable), `reviews` (integer, not-null default `0`), `price` (integer, not-null default `0`), `oldPrice`/`old_price` (integer, nullable), `colors` (text[] — color **names** only, e.g. `["Onyx Black", ...]`, not `{name,hex}` objects — `site-data.ts` re-attaches hex values from a shared lookup when building the frontend `Product` shape), `sizes` (text[]).
- `src/db/index.ts` only creates a `pg.Pool`/`drizzle` instance if `process.env.DATABASE_URL` is set; otherwise `db` is `null` and the app still builds/runs — any new DB-touching code must handle `db === null`. The pool passes `ssl: { rejectUnauthorized: false }` (Supabase requires TLS) and is memoized on `globalThis` to survive HMR in dev — **this means a running dev server keeps reusing the same `Pool` object across edits to `index.ts` itself**; if you change the `Pool`/`ssl` config, a Fast Refresh reload won't pick it up, only a full process restart will, since the memoized instance from before your edit is still sitting in `globalForDb`.
- `src/db/seed.ts` is a standalone script run via `npm run db:seed` (`tsx` + `bcryptjs`/`@types/bcryptjs` deps). It inserts all 12 `categories` and all ~96 `categoryProducts` items, plus one admin user. **The products upsert is `.onConflictDoUpdate()`, not `.onConflictDoNothing()`** — but scoped to *only* the 9 newer columns (`sport`/`badge`/`featured`/`rating`/`reviews`/`price`/`oldPrice`/`colors`/`sizes`) via `sql\`excluded.<column>\`` in the `set` clause. This is deliberate: re-running the seed needs to be able to backfill new columns onto already-seeded rows (plain `onConflictDoNothing` would just skip them since the slug already exists), but `name`/`description`/`fabric`/`tags`/`images`/`position` are excluded from that `set` on purpose so re-seeding can never clobber an edit made through the Admin Dashboard. If a future column gets added the same way, follow this same narrow-`set` pattern rather than upserting the whole row. The new columns are populated by matching each `categoryProducts` item to its counterpart in the static `products` array **by slug** (both were generated with the exact same slugify + collision-suffix logic from the same source data, so they line up 1:1 — see the comment in `seed.ts`). Categories/admin-user inserts are still plain `.onConflictDoNothing()`.
- **Deliberately does not import the shared `db` singleton from `./index`** in `seed.ts` — that module reads `process.env.DATABASE_URL` at top-level module-evaluation time, and ESM hoists all `import` evaluation ahead of a module's own statements, so by the time `seed.ts`'s own `dotenv.config({ path: ".env.local" })` call would run, `./index` would already have evaluated with an unset env var and frozen `db`/`pool` as `null`. `seed.ts` instead builds its own `Pool`/`drizzle` instance after calling `dotenv.config()` itself. Keep this pattern if `seed.ts` ever grows more scripts alongside it.
- `RESEND_API_KEY` also sits in `.env.local` but nothing in `src/` references it — a leftover from the abandoned Resend attempt on `contact-form` (see Forms below). Don't assume it's wired to anything live.
- **Price is a real, populated column now** (all `0` for the seeded catalog, since that's what the static data had) and the Admin Dashboard product form has a Price input — but the public site's "no price anywhere" UI decision (see Products page section below) was deliberately **not** reversed; price is stored and admin-editable but still never rendered on `/products`, `/products/[slug]`, or `wishlist`. Don't reintroduce price display without being asked.

### Products page (`src/app/(site)/products/page.tsx` + `products-explorer.tsx` + `product-card.tsx`) — fully reworked, dark theme, no prices, quote-driven

Was a light-themed page with a white sidebar/cards and real price filtering/sorting; is now dark end-to-end (`bg-[#0a0a0a]` explorer section, `#111`/`#222` cards), matching `/categories`' established dark convention, since the whole page shows no pricing anymore (see the `products` bullet under Data layer for how the underlying array was regenerated).

Don't reintroduce price UI on this page or its detail/wishlist siblings without being asked.

### Component composition

### Images

`next.config.ts` whitelists `images.pexels.com`, `images.unsplash.com`, and `res.cloudinary.com` as remote image hosts (all three must also be listed in the CSP `img-src` header in the same file, or `next/image` will 500 with an "Invalid src prop" error even though the host is in `remotePatterns` — this is a recurring gotcha, most recently hit again when Cloudinary was added for the gallery). Most product/testimonial imagery is remote Pexels URLs generated by helpers in `src/lib/data.ts`; `galleryImages` is Cloudinary (see Data layer above). The About page's two "Our Story" images used to be remote Unsplash URLs but are now local (`public/about/`, see below). **Restarting the dev server is required after editing `next.config.ts`** — Next does not hot-reload it. If a locally-replaced image file (same path, new bytes, e.g. someone drops a new photo in over an old filename) doesn't visibly update after a browser refresh — verify with `curl -I` that the `Content-Length` served actually matches the new file's size before assuming it's a cache problem. If it doesn't match, it's Next's on-disk image-optimizer cache (`.next/cache/images`): `rm -rf .next/cache/images` and restart. If that alone doesn't fix it, this has recurred at least once where nothing short of deleting the **entire** `.next` directory (`rm -rf .next`, not just `.next/cache/images`) and restarting cleanly actually resolved it — likely a stale prerendered-route cache from `generateStaticParams`, not just the image cache. Incognito/hard-refresh ruling out *browser* cache doesn't rule out this server-side one — they're independent layers, check both.
- Local asset folders in `public/` (no remote-host config needed): `hero1-4.png` (Hero carousel), `custom1-4.png` + `athlete-girl.jpg` (homepage "Custom apparel" grid — 4 tiles, each with its own `objectPosition` and a shared `#111111` container background, referenced directly by path in `page.tsx`, not through `data.ts`), `public/manufacturing/` (the 4 `processSteps` images — see Data layer above — plus reused by `/manufacturing`'s own `stageImages` override), `public/expertise/` (Our Expertise section), `public/featured/` (Featured Build section), `public/categories/` (both the homepage's `featuredCategories` override and `/categories`' own `categories` data point here, with different filenames — see Data layer above), `public/portfolio/` (Portfolio page collection cards), and `public/about/` (About page's "Our Story" images, `factory-sewing.png`/`quality-control.png`, `#111111` container backgrounds). **Recurring pattern**: a task will often name an exact path (e.g. `/foo/bar.jpg`) that doesn't exist yet, while a same-named-but-different-extension/case file already sits elsewhere (often the `public/` root); the fix each time has been creating the requested subfolder and copying the real file in under the exact requested name rather than assuming the asset needs to be sourced externally — check `public/` before asking or improvising a new image.
- `gallery-grid.tsx` renders `galleryImages` as a uniform CSS Grid (`grid-cols-1 sm:grid-cols-2 lg:grid-cols-3`, fixed `aspect-[4/3]` tiles, `object-cover`) — **not** CSS-columns masonry. It was originally a Pinterest-style `columns-*` masonry, but that broke down once real (non-uniform-aspect-ratio) Cloudinary photos replaced the old uniform stock images, causing column-balancing gaps and off-center crops; don't revert to `columns-*` without re-solving that (the Our Expertise / Featured Build / Portfolio grids all deliberately use real CSS Grid for the same reason). It also tracks a `hiddenIds` state set — each `Image`'s `onError` adds its `id` there, and items with a hidden `id` are filtered out of the rendered list entirely (so a broken/404 Cloudinary image disappears cleanly instead of showing a broken-image icon), plus a `loadedIds` set that fades each image in via `onLoad` (`opacity-0` → `opacity-100`) since Cloudinary images loading in with zero transition on a dark `bg-ink` tile looked indistinguishable from "broken" mid-load. There is deliberately **no** `placeholder="blur"`/`blurDataURL` on these images — one was added and then removed after the base64 placeholder rendered as a solid green box instead of blending in; if re-adding a blur placeholder, verify the decoded pixel color first rather than reusing a copy-pasted base64 string.

## Admin Dashboard (`/admin/*`)

A full CRUD admin panel over the DB, built in one pass. Routes: `/admin` (redirects to `/admin/dashboard`), `/admin/login`, `/admin/dashboard`, `/admin/products` (+`/new`, `/[id]/edit`), `/admin/categories`, `/admin/gallery`, `/admin/quotes`.

### Two separate root layouts — this is the single biggest structural change in the repo's history

Next.js App Router has exactly one applicable root layout per route by default, and the pre-existing `src/app/layout.tsx` (html/body, Navbar, Footer) wrapped *everything*, `/admin/*` included, with no way to opt a subtree out. The fix was Next's **multiple root layouts** recipe: every non-admin route moved into a new `src/app/(site)/` route group (route groups don't affect URLs — `/about` etc. are unchanged) with its own `src/app/(site)/layout.tsx` carrying the old html/body/Navbar/Footer/metadata; `src/app/admin/layout.tsx` is a second, independent root layout (own `<html>/<body>`, `bg-[#0a0a0a]`, `robots: noindex`, **no** Navbar/Footer/announcement bar). The original top-level `src/app/layout.tsx` no longer exists — **if you ever see a bare `src/app/layout.tsx` reappear, someone tried to "simplify" this back into a single layout and just broke the admin isolation.** Both roots import the same font instances from `src/lib/fonts.ts` (a shared module was needed since `next/font/google` calls must live in each root that uses them). Nested under `src/app/admin/` there's a further `(panel)` route group whose `layout.tsx` renders the sidebar+topbar shell — this wraps every admin route *except* `/admin/login`, so the login page renders standalone inside the admin root layout with no sidebar. If asked to move something from `src/app/foo/` into this tree, remember it now needs to land under `(site)` to keep the public shell, not directly under `app/`.
- A `.next` full wipe (`rm -rf .next`, not just `.next/cache/images`) was required immediately after this move — Next's route-manifest cache goes stale on a route-group restructure like this and threw phantom `Cannot find module '.../src/app/layout.js'` errors from `.next/dev/types/validator.ts` until cleared. Expect the same if this structure changes again.

### Auth

`src/lib/admin-auth.ts` — `jose` (not `jsonwebtoken`; edge-runtime compatible, needed since middleware/proxy below runs on the edge) signs/verifies a JWT (`{ sub: adminId, email }`, HS256, 7-day expiry, secret from `SESSION_SECRET` in `.env.local`) stored in an httpOnly cookie (`admin_session`, `sameSite: lax`, `secure` in production). `getAdminSession()` reads it via `next/headers` for server components/route handlers; `requireAdminSession()` is the same thing, called at the top of every `/api/admin/*` route handler as defense-in-depth.
- `src/proxy.ts` (Next.js 16 renamed the `middleware.ts` file convention to `proxy.ts` / `export function proxy()` — same mechanism, new name; a stray `middleware.ts` reappearing means someone reverted to the old convention, which still logs a deprecation warning but keep using `proxy.ts` going forward) has `matcher: ["/admin/:path*", "/api/admin/:path*"]` — **both** prefixes matter, it's easy to protect only the page routes and forget the API routes are a separate matcher prefix. `/admin/login` and `/api/admin/login` are explicitly excluded from the auth check (the login page redirects *to* dashboard if already authenticated instead). Unauthenticated requests get redirected to `/admin/login` for page routes, or a `401 { ok: false }` JSON response for `/api/*` routes (checked via `pathname.startsWith("/api/")`) — don't collapse this into a single redirect-everything behavior, an API caller doesn't want an HTML redirect response.
- Login: `POST /api/admin/login` looks up `adminUsers` by email, `bcrypt.compare`s the password, signs and sets the cookie. `POST /api/admin/logout` clears it. Seeded admin credentials: `admin@blackshark.com` — see Known repo state below for the password-rotation caveat.

### Dashboard charts (`src/components/admin/charts/`, `recharts` `^3.10.1`)

Three charts, all real Supabase queries, all dark-themed via a shared `ChartTooltip` component (`content={(props) => <ChartTooltip {...props} />}` — recharts v3's `content` prop needs the function form, not a bare `<ChartTooltip />` element, or TypeScript complains the element is missing required props since it doesn't know recharts injects them at runtime; the exact type to import is `TooltipContentProps` from `"recharts"`, not `TooltipProps`, which is the *shape recharts hands to your renderer*, not what a bare element needs). `QuotesBarChart` (last 6 months of `quoteRequests`, zero-filled via a JS-generated month list rather than assuming the DB has a row for every month), `CategoryPieChart` (donut + a custom 2-column legend grid at `text-[11px]` — an earlier single-column flex layout with `truncate` clipped long names like "Youth Sportswear"; don't reintroduce `truncate` here), `CategoryBarChart` (horizontal bars, all 12 categories via a left join so a zero-product category still shows). Dashboard stat cards (`stat-cards-grid.tsx`) show a genuinely-computed "% change" (current DB count vs. count as of 30 days ago via `created_at <= now() - interval '30 days'`, or 30-day request volume for quotes) — not a fabricated number; because the whole catalog was seeded within one recent session, these mostly read 0% right now, which is correct, not broken.

### Products/Categories/Gallery/Quotes CRUD pages

All under `src/app/admin/(panel)/`, all client components that call their own `/api/admin/*` REST endpoints (no server-fetched initial data — simpler and consistent across all four, at the cost of an extra round-trip). `src/lib/admin-products.ts` (`parseProductFields`) is shared body-parsing/validation used by both `POST /api/admin/products` and `PUT /api/admin/products/[id]` — extend that one function, not each route handler separately, if a product field's validation needs to change. The product create/edit form (`product-form.tsx`) covers every `products` column including the 9 added later (Sport dropdown sourced from the same `sports` array as the public site's filter, Badge dropdown None/New/Best Seller/Sale, Featured toggle, Rating/Reviews/Price number inputs) — but **not** `oldPrice`/`colors`/`sizes`, which were never asked for as form fields and stay whatever the seed or a previous edit set them to.
- Image upload: `POST /api/admin/upload` (generic — accepts `file` + a `folder` string, e.g. `categories/team-uniforms` or `gallery`; validates PNG/JPEG/WebP, 10MB cap, rejects unsafe folder strings via a regex allowlist) writes with Node's `fs/promises` straight into `public/<folder>/`. **This works in local dev and on any host with a persistent, writable filesystem — it will NOT work on Vercel or other serverless deployments**, where `public/` is read-only at runtime after build. If this app ever deploys to Vercel, uploads need to move to Supabase Storage/S3/similar before that's discovered as a silent production failure. `image-uploader.tsx` is the reusable multi-image picker (drag-to-reorder via native HTML5 drag events, no library) used by the product form and (single-image mode) the category form; the gallery page has its own upload flow with a tag selector since it batches multiple images with one shared tag per batch.
- Deleting a category whose slug still has products (`categorySlug` FK) is caught and returned as a `409` with a clear message rather than a raw Postgres FK-violation 500 — see `DELETE /api/admin/categories/[id]`.

## Known repo state to be aware of

- `.env.local` in this working tree contains a live Supabase Postgres connection string (and an unused `RESEND_API_KEY`, see Database section) with real credentials — do not print, log, or commit its contents.
- `package.json`'s `name` field is still the generic `"nextjs-postgresql-template"` leftover from the starter template, not the actual project name.
- A real `admin_users` row exists in Supabase (`admin@blackshark.com`, bcrypt-hashed password) and there's now a real login at `/admin/login` that uses it — the plaintext password was shared directly in a past chat request (and again when creating a test product via the API during verification), so it should be treated as already-exposed and rotated before any real production use.
- `.env.local` also has a `SESSION_SECRET` (random 32-byte hex, generated for this repo) used to sign the admin JWT — same "don't print/log/commit" rule as `DATABASE_URL`. If it's ever rotated, every existing admin session cookie becomes invalid (that's fine, just log in again) — no data loss, it's not used for anything but signing.
